# 29. TypeScript is transpiled by Oxc in an optional crate outside the engine, on a worker thread sized for its input

Date: 2026-11-16

## Status

Accepted

## Context

Embedders want to run `.ts` and `.tsx` files without a build step, as Node (`--experimental-strip-types`), Deno and Bun do (TASK-103.13). TypeScript at run time means two things:

- **Level 1, erasable syntax.** Type annotations, interfaces, type aliases, `declare`, type-only imports and exports, `as`, `satisfies`, `!`, type arguments and `implements` disappear and leave a valid JavaScript program. This is what Node's strip-only mode accepts, and what TypeScript's `--erasableSyntaxOnly` allows.
- **Level 2, syntax with run-time meaning.** `enum`, namespaces with values, parameter properties, `import x = require()`, `export =`, decorators and JSX produce code; they need a transform, not just deletion.

Type checking is out of scope. Neither level needs it, and `tsrs` (the experimental Rust port of the checker) stays a possible tooling option.

The engine already takes what a transpiler produces. The host loads a module as `ModuleSource::SourceWithMap { source, source_map }` or registers a map for a script with `Engine::set_source_map` (ADR 0024), and from then on `Error.stack`, `Exception::stack`, CallSite objects and the debugger, with CDP, report original positions. A TypeScript front end therefore only has to turn `.ts` text into JavaScript text and a Source Map v3, and never has to reach into the engine.

Three ways to get there were considered.

**A strip-only transform in our own parser.** `agnijs-js-parser` would learn the type grammar (annotations, generics with their arrow-function and JSX ambiguities, every declaration form, `abstract`, overloads, accessibility modifiers) and blank the TypeScript tokens with spaces, as Node's `amaro` does with swc, so positions stay the same and no map is needed. It would be the smallest binary and the fastest path. But the type grammar is most of TypeScript's syntax and changes with every TypeScript release; it would live in the engine's parser, which test262 and the native stack budget guard and which every embedder ships, whether it runs TypeScript or not (ADR 0007, ADR 0016). And it covers level 1 only: enums, namespaces, parameter properties, decorators and JSX would still need a second tool.

**swc** (`swc_ecma_parser` and `swc_ecma_transforms_typescript`, Apache-2.0). Mature, and it guards its parser's recursion with `stacker`. It is a larger dependency tree than Oxc's for the same result (a TypeScript strip, the JSX and decorator transforms and a code generator with source maps) and its crates version independently, so a pin covers a dozen moving parts.

**Oxc** (`oxc_parser`, `oxc_semantic`, `oxc_transformer`, `oxc_codegen`, MIT; `oxc_sourcemap`, BSD-3-Clause). One project, one version number across its crates, a TypeScript parser that keeps up with TypeScript (0.158 parses 5.9 syntax, `import defer` included), a transformer that does both levels (TypeScript, legacy decorators with metadata, classic and automatic JSX) and a code generator that writes the source map as it prints. Measured on 2026-11-16 at 0.158.0 with rustc 1.99.0 on x86_64-pc-windows-msvc (16 threads), building the pipeline alone (parse, semantic, transform, print with a map):

| | |
| --- | --- |
| Packages added to `Cargo.lock` | 68 (21 of them Oxc's own); no version of a package already locked changes |
| Clean build, release | 51 s |
| Clean build, debug | 30 s |
| Binary size, `size` profile (stripped, fat LTO) | 2.50 MB (2,631,168 bytes against 133,632 for an empty program) |
| MSRV | Rust 1.97 (0.158); 0.159, released the same day, needs 1.98 |

Three facts about Oxc shape the decision as much as its features:

- **It releases weekly, each time a breaking minor version**, and raises its MSRV with stable Rust (1.97 at 0.158, 1.98 at 0.159). The workspace MSRV is 1.88.
- **It has no recursion guard.** Its parser, semantic analysis, transformer and code generator are all recursive. On an 8 MiB stack, 10,000 nested parentheses, generic arguments or arrow functions, or 100,000 chained `+1`, `.b` or `()`, overflow the stack, which aborts the process: it is not a panic and cannot be caught. Measured in release, the deepest pattern costs 451 bytes of stack per byte of source (nested parentheses, 901 bytes per level) and 1,124 bytes per level for nested generics; in a debug build, 1,704 bytes per source byte. A lexical pre-scan cannot bound this soundly: regex-or-division and JSX text are decided by the parser, so a scan can be made to disagree with it about what is code.
- **Some of its output assumes a bundler.** By default the decorator helpers come from `require("@oxc-project/runtime/...")`, the automatic JSX runtime from `require("react/jsx-runtime")` in scripts, and `export =` becomes `module.exports`. TC39 decorators (not TypeScript's legacy form) and `accessor` fields are passed through untransformed, and the engine does not parse them (ADR 0025).

## Decision

**Oxc is the TypeScript front end, in an optional crate, `agnijs-js-typescript`, that no engine crate depends on.** It is the same kind of seam as the Node resolver (ADR 0023): a library the embedder calls before handing code to the engine, typically from `Host::load_module`. The rules follow the RegExp, Intl and Temporal seams (ADR 0013, ADR 0015, ADR 0027):

- **The crate exposes only its own types.** `transpile(source, &Options) -> Result<Output, Error>`, where `Output` is `{ code: String, source_map: String }` and `Error` is our own (below). Options are our own enums and booleans; no Oxc type, diagnostic or allocator appears in its API, so an Oxc upgrade or a replacement touches one crate. The crate does not depend on `agnijs-engine-api` either: an embedder passes `code` and `source_map` to `ModuleSource::SourceWithMap` or to `eval_script` and `set_source_map`.
- **Both levels, chosen by `Options::mode`.** `Mode::Transform` (the default) runs Oxc's TypeScript transform: types are stripped and `enum` (`const enum` included, emitted as a plain enum, as `isolatedModules` requires), namespaces, parameter properties and, when `Options::experimental_decorators` is set, legacy decorators (with `emit_decorator_metadata` optional) are transformed. `Mode::StripOnly` accepts only erasable syntax, as Node's strip-only mode and `--erasableSyntaxOnly` do, and reports every enum, namespace with values, parameter property, `import =` and `export =` as an error with its position. Types are never checked. Positions come from the source map in both modes; we do not blank types in place, since every position the engine reports already goes through the map.
- **What runs is ECMAScript the engine parses, with no imports added.** The target is `esnext`, so nothing but TypeScript and JSX is lowered. JSX uses the classic runtime (`React.createElement` and `React.Fragment` by default, both configurable as `jsx_factory` and `jsx_fragment_factory`, as in `tsconfig.json`); the automatic runtime is an option that emits an `import` from `jsx_import_source` and is refused in scripts. Decorator helpers are Oxc's `External` mode (`babelHelpers.decorate`, `decorateParam`, `decorateMetadata`); the crate prepends our own implementations of the three, written for this crate from the TypeScript emit semantics, on one line before the output, and shifts the map by that line. The crate refuses, with a position, what would not run: decorators without `experimental_decorators` (TC39 decorators, which neither Oxc nor the engine implements), `accessor` fields, and the CommonJS forms (`import x = require()`, `export =`). `Options::verbatim_module_syntax` keeps imports that are never used as values, as TypeScript's flag of that name does; by default they are removed, as `tsc` removes them.
- **Modules and scripts are the embedder's choice.** `Options::kind` is `Module` or `Script` and must match how the code will be run (`load_module` or `eval_script`); `Options::jsx` turns on the `.tsx` grammar. `Options::for_path` derives both from a file name (`.ts` and `.mts` modules, `.cts` script, `.tsx` module with JSX).
- **Errors are diagnostics with positions.** `Error::Syntax(Vec<Diagnostic>)` carries every parse, early and transform error Oxc reports, and the crate's own refusals, each with a message, an optional help text, the byte range in the source and a 1-based line and column, the column counted in UTF-16 units as the engine counts them (ADR 0024). `Error` also has `TooLarge` (input over `max_source_len`), `Resource` (the worker thread could not be started) and `Internal` (Oxc panicked: a bug, reported as an error, never unwound into the caller). `Error` is `#[non_exhaustive]` and implements `std::error::Error`; its `Display` prints `name:line:column: message` lines.
- **Oxc runs on a worker thread whose stack is sized from the input.** Each call spawns one thread with a stack of 16 MiB plus 1 KiB per byte of source in release (2.2 times the deepest measured cost) and 4 KiB per byte in debug builds, runs the whole pipeline there, and joins it. The stack is reserved address space, committed only as deep as the input actually nests, so ordinary code touches a few hundred kilobytes, and no input up to `max_source_len` can overflow it. `max_source_len` defaults to 1 MiB (a 1 GiB reservation in release) and can be lowered for untrusted input, or raised. A hostile input within the limit can touch up to the reservation, so the limit is also the memory bound. On targets without threads (`wasm32-unknown-unknown`) the pipeline runs on the caller's stack and is safe only for trusted input; the crate documents it.
- **Transpiling is host work, outside fuel and interrupts.** It happens before the engine sees any code, so `Engine::set_fuel`, `Host::interrupt` and the memory limit do not apply to it; Oxc has no cancellation. Its time and memory grow linearly with the input, which `max_source_len` bounds. A host that takes TypeScript from untrusted sources sets that limit, and may run `transpile` on a thread of its own with a timeout.
- **Determinism.** The output and the map depend only on the source and the options: Oxc's hash maps use a fixed hasher, its only random-number generator runs at build time inside a perfect-hash macro, and the code generator writes tabs and `\n` on every platform. The fixture suite compares outputs byte for byte on Linux, Windows and macOS, and a test transpiles each fixture twice. Transpiled code then runs under the engine's determinism rules (`docs/determinism.md`) unchanged.
- **Out of the default build, the C API and the engine's MSRV.** No engine crate (`agnijs-js-vm`, the compiler and parser, `agnijs-engine-api`, `agnijs`, `agnijs-capi`) lists the crate, so the default build, its binary size and its dependency graph are unchanged, and `boundary.rs` gains a test that keeps it so. The C API gets nothing now; a C entry point would be an ABI addition behind a cargo feature of `agnijs-capi`, decided separately. The crate declares `rust-version = "1.97"`, Oxc's, as the JIT crate declares its own; the `msrv` CI job leaves it out, as it leaves out the JIT crate and the command. The `agnijs` command gets a `typescript` feature, off by default, that runs `.ts`, `.mts`, `.cts` and `.tsx` files; the fuzz crate gets one too. The workspace build and the `standalone` job exclude the crate (`--exclude agnijs-js-typescript`), and a `typescript` CI job builds and tests it on Linux, Windows and macOS with its fixture suite and clippy.
- **Version pinning.** The Oxc crates are pinned exactly (`=0.158.0`), all to the same version, and move together in a commit that runs the fixture suite, the crate's tests and the fuzz target, never through `cargo update` alone. A new version is taken when it fixes something we need or every few months, not weekly, and only once it is at least a week old; the crate's `rust-version` follows the pinned Oxc's.
- **Fallback.** The API is ours, so if Oxc stops being usable (licence, maintenance, a regression the pin cannot avoid) the crate can be rebuilt on swc behind the same `transpile` without touching an embedder. Until then the pin stays where it is; nothing in the engine waits on Oxc.

## Consequences

- Embedders run TypeScript by adding one crate and one call in their module loader, and get original `.ts` positions in `Error.stack`, `Exception::stack`, CallSite objects and the debugger through the engine's existing source-map path. The CDP adapter sends the map to DevTools, which places breakpoints in the `.ts` file.
- Builds that do not use the crate pay nothing: no size, no compile time, no MSRV change. Builds that do pay about 2.5 MB of binary and 30 to 50 s of clean compile time, and need Rust 1.97.
- Oxc's weekly breaking releases are absorbed by the exact pin and the seam; each move is deliberate and tested.
- Transpiling a file costs one thread spawn and a stack reservation proportional to its size. Pathological nesting within `max_source_len` costs memory up to that reservation instead of crashing the process; that memory bound, not the engine's limits, is what protects a host from hostile TypeScript.
- TC39 decorators wait for the engine (ADR 0025) and for Oxc; TypeScript code using them gets a clear error, not a silent change of semantics. Code written for `tsc`'s CommonJS output (`import =`, `export =`) must move to ES module syntax.
- The fixture suite under `crates/agnijs-js-typescript/tests/fixtures` pins the supported syntax, each refusal and the TypeScript level (5.9 syntax through Oxc 0.158), and runs in CI with the fuzz target.

# Stability and versioning

This page says which AgniJS interfaces you can build on, how each one is versioned, and how it may change. It only states what the code and CI enforce today. Where a policy is not decided yet, it says so and names the task that decides it.

AgniJS is pre-release (workspace version `0.3.0`; changes per version are in [CHANGELOG.md](../CHANGELOG.md)). Nothing is published to crates.io, there are no tagged releases, and the crate names may still change. Until the first release, "a change" below means a commit to `main`.

| Interface | Versioned by | Compatibility today |
| --- | --- | --- |
| [C API (ABI)](#the-c-api) | `AGNIJS_ABI_VERSION_MAJOR`/`MINOR`, `agnijs_abi_version()` | Append-only within major 1; enforced by the generated header and `struct_size` checks |
| [Rust API](#the-rust-api) | Cargo version, now `0.3.0` | Semver for `agnijs` and `agnijs-engine-api`: a breaking change bumps the minor version before 1.0; checked by `cargo-semver-checks` in CI |
| [Bytecode](#bytecode-and-snapshots) | Format tag `agnijs-bc-N` | Loads only in the build that wrote it; anything else is refused, never misread |
| [Snapshots](#bytecode-and-snapshots) | Tag `agnijs-snap-N+agnijs-bc-M` and native-registry fingerprint | Same build only; anything else is refused |
| [CLI](#the-agnijs-cli) | `agnijs --version` | Documented flags and exit codes; no compatibility promise yet |
| [CDP](#the-devtools-protocol) | Chrome DevTools Protocol 1.3 subset | The methods implemented, not a promise about future ones |
| [Minimum Rust](#minimum-supported-rust-version) | `rust-version` in `Cargo.toml` | 1.88 for the workspace, built in CI; 1.95 for the CLI, 1.97 for the JIT crate |

## The C API

The C API is the one interface with a compatibility promise now. The details are in [c-api.md](c-api.md#versioned-structs-and-the-abi) and ADR 0021; in short:

- **Version numbers.** The header defines `AGNIJS_ABI_VERSION_MAJOR` and `AGNIJS_ABI_VERSION_MINOR` (now 1.2). `agnijs_abi_version()` returns `major << 16 | minor` for the library actually loaded. A program checks at start-up that the major matches the header it was built against.
- **Minor versions add.** Within major version 1, functions, constants and struct fields are only added, struct fields only at the end, and each addition bumps the minor version. Nothing is reordered, removed or retyped, and an existing status code keeps its meaning. The history so far: 1.1 added the fuel limit and the random seed to `AgnijsEngineOptions`, 1.2 added source maps.
- **Versioned structs.** Every struct passed across the boundary starts with `struct_size`. The library refuses a smaller size than it knows. It accepts a larger one, from a program built against a newer header, only when the extra bytes are zero, that is, when the program left the newer fields at their defaults. So a program built against 1.N runs against a library 1.M with M ≥ N, and also against an older one as long as it does not use what that library lacks.
- **Major versions break.** Any incompatible change bumps the major version. Nothing removed is kept behind a deprecation period within a major version, because removal itself is a major change.
- **What enforces it.** The header is generated by cbindgen, and CI regenerates it and fails on any difference (`capi-checks` job), so the header always matches the library. The `struct_size` rules are tested in `crates/agnijs-capi/tests/hostile.rs`. Nothing in CI yet compares the ABI with the previous version's to catch a removal or a reordered field; that is reviewed by hand.

The C API also promises behaviour across all versions: it never unwinds a Rust panic into C, and it refuses invalid ids and arguments with a status code rather than crashing ([c-api.md](c-api.md#what-never-happens-and-what-still-can)).

## The Rust API

The Rust API follows Cargo's semver rules, and CI checks every change against them ([ADR 0026](adr/0026-the-agnijs-crate-is-the-public-embedding-surface-over-the-engine-interface.md), TASK-104).

**What is public.** Two crates:

- `agnijs`: `Context` and its helpers, `new_engine`, `new_engine_from_snapshot`, and `agnijs::api`, which re-exports the next crate;
- `agnijs-engine-api`: the engine interface (`Engine`, `Host`, `Value`, `Handle`, `Error`, the host function and host object types), with the contracts in its rustdoc: [handle lifetimes](../crates/agnijs-engine-api/src/value.rs), the host function and host object rules, and the error mapping.

The `#[derive(HostClass)]` and `#[host_methods]` macros are public through `agnijs`; `agnijs-derive`, which implements them, is not public on its own. Items marked `#[doc(hidden)]` (the handle registry, the bytecode container helpers, the conformance kit) are for engine implementors in this workspace and are outside the policy. Every other crate is internal and may change in any commit: the VM, compiler, parser, regex and Intl crates, the JIT, the QuickJS-NG adapter, the CLI, the fuzz, bench and test262 crates, and the Rust side of the C API (whose C ABI has its own rules above). `agnijs-js-resolve`, the debugger capability and `agnijs-js-cdp` are meant for embedders but stay outside the policy until their interfaces are reviewed.

**What is breaking.** Anything Cargo's [semver reference](https://doc.rust-lang.org/cargo/reference/semver.html) calls a major change to a public item, which `cargo-semver-checks` reports, and any change to a documented contract that a correct embedder could observe, such as when a dropped handle is released, which errors a host function's result maps to, or when finalizers run. Not breaking:

- a new variant of `Error`, `agnijs::Error` or one of the hook enums (`ModuleSource`, `ConsoleLevel`, `RejectionEvent`, `RegexMatcher`, `ErrorKind`), which are `#[non_exhaustive]`. A `match` on them outside `agnijs-engine-api` needs a wildcard arm, and each enum's rustdoc says what to do with a variant you do not know;
- new items, and new methods on `Engine`, with or without a default body: `Engine` is sealed (embedders call it but cannot implement it). A new `Host` method, which embedders do implement, always has a default body;
- changes to internal crates and hidden items, and bytecode or snapshot format changes, which are versioned by their own tags ([below](#bytecode-and-snapshots));
- raising the MSRV, under the rule [below](#minimum-supported-rust-version).

Every other public enum is exhaustive (`Value`, `PropertyKey`, `TypeOf`, `HeapKind`, `PromiseState`), so a new variant in one of them is breaking.

A `RealmId`, like a `Handle`, carries the engine that issued it: another engine refuses it with `UnknownRealm`, whatever its index ([value.rs](../crates/agnijs-engine-api/src/value.rs)). Its fields are private; an embedder gets realm ids only from `main_realm` and `create_realm`.

**How versions move.** All crates share the workspace version, now `0.3.0`; [CHANGELOG.md](../CHANGELOG.md) lists what each version changed.

- **Before 1.0** (now, and after a first `0.x` publish): a breaking change bumps the minor version (`0.3.0` to `0.4.0`) in the same commit or pull request. Other changes do not need a bump, except a patch bump when `cargo-semver-checks` asks for one (for example, when an item is newly deprecated). Nothing is published yet, so the version is how a git-pinned embedder such as Gable tells whether moving its pin can break it.
- **From 1.0**: a breaking change bumps the major version, and is preceded by at least one minor release in which the replaced item is `#[deprecated]` with a pointer to its replacement. New features bump the minor version, fixes the patch version.

**What enforces it.** The `semver` job in `ci.yml` runs `cargo-semver-checks` on `agnijs` and `agnijs-engine-api`, comparing the change with its base: the pull request's base, or the commit before the push. It fails when the change needs a bigger version bump than it makes. Contract changes the tool cannot see are reviewed by hand, and the contract tests (`crates/agnijs/tests/lifetimes.rs`, `host_contract.rs`) catch the ones they cover. To check locally: `cargo semver-checks -p agnijs -p agnijs-engine-api --baseline-rev origin/main`.

Behaviour you can rely on regardless: the engine poisons itself rather than continuing after a panic ([security-model.md](security-model.md#panics-in-the-rust-api)), and the limits in the security model hold.

## Bytecode and snapshots

Bytecode and snapshots are caches tied to one engine build, not an interchange format (ADR 0010, ADR 0022):

- **Bytecode** is an `AGJS` container whose format tag pins the compiler: now `agnijs-bc-8`. Any change to the instruction set, the constant pool or the payload layout changes the tag. A container with another tag fails to load with `BytecodeMismatch`, and a damaged one with `BytecodeCorrupt`, before any payload byte is interpreted. Bytecode written by an older or newer build is never migrated or reinterpreted: the host keeps the source and recompiles. Every tag change so far is recorded in ADR 0010's addenda.
- **Snapshots** carry the tag `agnijs-snap-N+agnijs-bc-M` (now `agnijs-snap-2+agnijs-bc-8`) and a fingerprint of the native-function registry and the crate version, so a snapshot taken by a build with a different set of built-ins, or another version, is a `BytecodeMismatch` too.
- **Same version, other build.** The tag pins the format, not the binary. A snapshot from a build with different cargo features (for example `intl`) differs in its registry fingerprint and is refused. Bytecode from a build without the `linear-regex` feature loads, but marks every pattern ineligible for the linear matcher ([security-model.md](security-model.md#regular-expressions-redos)).

What is promised is that a mismatch is always an error, never a crash or a misreading; this is tested and fuzzed (`docs/fuzzing.md`, the `bytecode` and `snapshot` targets). Bytecode and snapshots are trusted input: the checksum catches accidents, not attackers ([security-model.md](security-model.md#bytecode-and-snapshots-are-trusted-input)).

Once there are releases, a tag will still change with every format change; whether a release may load the previous release's format is not decided.

## The `agnijs` CLI

The command-line tool's commands (`run`, `eval`, `repl`, `compile`, `snapshot`), flags and exit codes (1 uncaught exception, 2 usage, 3 fuel or memory limit, 13 unsettled top-level await, 130 interrupted) are documented in `crates/agnijs-cli/README.md` and tested in `crates/agnijs-cli/tests`. They are a development and testing tool, and there is no compatibility promise for them yet: a flag may be renamed or removed in any commit. Files written by `agnijs compile` and `agnijs snapshot` follow the bytecode and snapshot rules above.

## The DevTools protocol

`agnijs-js-cdp` speaks a subset of the Chrome DevTools Protocol: the `Runtime` and `Debugger` domains and the `/json` discovery routes, reporting protocol version 1.3. The protocol is Chrome's; AgniJS follows what Chrome DevTools and VS Code send. A method it does not implement gets the standard error response (`-32601`, "'Method' wasn't found"), so a client can probe. Which methods are implemented may grow or change in any commit. The CDP endpoint is a development tool and full control of the engine ([security-model.md](security-model.md#the-debugger-and-the-cdp-endpoint-are-full-control)).

## Minimum supported Rust version

The workspace sets `rust-version = "1.88"`, the oldest toolchain its default build compiles with (ICU4X 2.x, behind the default `intl` feature, sets it). Two crates declare their own, newer minimum: the `agnijs` command 1.95 (rustyline 19 uses `cfg_select!`), a binary and not part of the embedding surface, and the JIT crate (the `jit` feature, opt-in) 1.97, which follows the toolchain its code generator needs.

Raising the workspace MSRV is not a breaking change, but it is done only in a minor version, never in a patch release: before 1.0 it bumps the minor version, from 1.0 at least the minor version. The new MSRV is at least six months old (four stable releases) when it is raised. The command's and the JIT crate's minimums may be raised with the minor version too.

The `msrv` job in `ci.yml` builds the workspace's default features with the toolchain `rust-version` names, leaving out the command and the JIT crate. Before it existed the workspace declared 1.85, which its dependencies had outgrown; 0.3.0 declares the real minimum.

## Decisions still open

These need the owner's decision and are recorded in TASK-103.18's and TASK-104's notes:

- Whether a release loads the previous release's bytecode and snapshot formats, or bytecode stays a same-build cache.
- Whether the CLI's flags and exit codes get a compatibility promise at the first release.
- Whether CI should compare the C ABI against the last release (for example with `abi-dumper` or a symbol and struct-layout diff) instead of relying on review.
